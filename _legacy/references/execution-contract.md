已有授权 → **直接执行，不重复确认**。仅当会改变 surface、商业含义、安全声明、假指标或交付格式时才提问。

## 2. 内容与架构

- 每个模块回答一个**具体读者问题**；展示明确的 **输入 → 处理 → 输出**（缺一不可就写缺口）。
- 每条连线有准确含义，并区分：**数据流** / **调用关系** / **业务顺序**；禁止无名箭头。
- 不要用通用功能文案（「智能」「一站式」「赋能」）填满页面。
- 架构页：平台边界、模块职责、连线语义必须可核对；不确定处标注假设，不装作既成事实。

---

## 3. 证据

| 类型 | 允许 | 禁止 |
|------|------|------|
| 事实 | 用户提供的数据、截图、官方素材 | 编造客户名、运行结果、收益数字 |
| 计算结果 | 标明公式/口径后的派生值 | 把估算写成实测 |
| 能力示例 | 标明「示例 / 示意」 | 冒充产品截图 |
| 概念示意 | 标明「概念示意」 | 当证据用 |

缺少证据 → **说明缺口**，继续用可用事实设计；不虚构产品界面、运行结果或 ROI。

---

## 4. 修改方式

- 根据**新内容**重新判断布局；禁止把新增要求简单堆进旧版留白。
- 保留已确认的事实与产品关系；必要时重构信息层级，而不是只加一块卡片。
- 每轮改完后，用 §0 约束账本做一次全量 diff 自检。

## 5. 交付前验收（从最终导出文件重新渲染）

文件能打开、lint/校验通过 **≠** 内容与设计合格。下列四项须在**最终交付物**上实际检查（不要声称做了未做的检查）：

1. **品牌** — 官方 Logo 已嵌入；底色与 logo 变体匹配；无文字伪 logo  
2. **语义** — 平台边界、模块职责、连线关系准确  
3. **内容** — 数字、单位、来源、示意标记完整；无未标注虚构  
4. **视觉** — 无溢出、乱码、错误换行、遮挡、过度密集  

发现问题 → **先修复再交付**。无法解决的限制在最终回复中明确写出。
