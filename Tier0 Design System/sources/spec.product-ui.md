# Tier0 Frontend Design Guidelines

## 1. 文档定位

本文件是 Tier0 前端的 UI 规范入口，用于在开发或调整页面、弹窗、表单、表格、卡片、导航等界面前快速统一设计判断。

它负责回答 4 个问题：

- Tier0 的产品界面应该呈现什么气质
- UI 设计的事实来源在哪里
- 新页面和新组件必须遵守哪些视觉与交互规则
- 更细的 token、主题和共享组件应去哪里查

本文件不负责：

- Monorepo、路由、BFF、proto、提交门禁等工程规范
- 组件源码级 API 说明
- 逐像素的页面实现细节

以上内容以 `CLAUDE.md`、`packages/theme`、`packages/ui` 和业务代码为准。

## 2. 设计目标

Tier0 的界面应当呈现以下特征：

- 精确、克制、偏产品工具，而不是营销落地页
- 高密度、可操作、偏 enterprise workspace
- 通过排版、边框、分层和节奏建立层级，而不是依赖重装饰
- 以中性色为主，以 FX Green 作为强调色，而不是满屏主色铺陈

默认视觉方向：

- 背景以白、浅灰、近黑为主
- 核心主操作使用近黑色
- 高亮、选中、进行中、激活态优先使用 FX Green
- 避免大面积渐变、装饰性图形、厚重阴影和过强的拟物效果

## 3. 事实来源

做 UI 时，先看代码里的事实来源，不要在业务页面重新发明一套规则。

- 全局主题入口：`packages/theme/src/index.scss`
- 语义化主题变量：`packages/theme/src/themes.scss`
- 原始色板变量：`packages/theme/src/variables.scss`
- Tailwind token 与排版工具：`packages/theme/src/tailwind.css`
- Ant Design token 桥接：`packages/theme/src/token.ts`
- Ant Design 覆盖样式：`packages/theme/src/override-antd.scss`
- 共享组件：`packages/ui/components`

优先使用语义 token 和共享组件，不要优先写局部样式覆盖。

## 4. 设计原则

### 4.1 层级优先

界面层级优先通过以下方式建立：

- 标题与正文的字号、字重差异
- 背景层次变化
- 边框和分隔线
- 模块间距与布局节奏

不要依赖这些方式作为主要层级手段：

- 大面积艳色背景
- 装饰性插画
- 无意义的阴影堆叠
- 过多渐变和动画

### 4.2 高密度优先

Tier0 多数页面是工作台，不是展示页。默认采用高密度布局：

- 表单、筛选、表格、侧栏、弹窗优先紧凑排布
- 内容区域优先服务操作效率和信息读取
- 页面主体通常是 header + controls + content 的 workspace 结构

除登录、引导、创建向导等少数场景外，不要把内部产品页做成居中展示型 landing page。

### 4.3 语义优先

颜色、状态、组件都应表达明确语义：

- 黑色系承担核心操作与主要文字
- 绿色承担高亮、激活、选中、进度、正向动作提示
- success / warning / error / info 使用既有状态 token
- 不要把 FX Green 当作“通用成功绿”到处滥用

## 5. 基础视觉规则

### 5.1 颜色

颜色使用顺序：

1. 优先使用 `--tier0-*` 语义变量
2. 其次使用 Tailwind 映射后的语义 class
3. 最后才考虑极少量局部补充

常用语义：

- 页面/容器背景：`--tier0-bg-color`、`bg-bg`
- 次级背景：`--tier0-bg-secondary`、`bg-bg-secondary`
- 选中/强调背景：`--tier0-bg-accent`、`bg-bg-accent`
- 弱强调背景：`--tier0-highlight-bg-accent`、`bg-highlight-bg-accent`
- 主文字：`--tier0-text-color`、`text-text`
- 次级文字：`--tier0-text-secondary`、`text-text-secondary`
- 弱文字：`--tier0-text-tertiary`、`text-text-tertiary`
- 标准边框：`--tier0-border`、`border-border`
- 主按钮：`bg-button-primary`
- 高亮按钮：`bg-button-highlight`

禁止：

- 在业务页面硬编码十六进制颜色作为常规方案
- 引入不在主题体系中的“新主色”
- 默认使用 IBM Blue、紫色系、米棕系、重暗色系作为产品主视觉

### 5.2 排版

默认文本使用应用主字体，不自行混入新的字体体系。

优先复用现有排版工具：

- 大标题：`typo-h1`
- 分区标题：`typo-h2`
- 子标题：`typo-h3`
- 面板标题：`typo-h4`
- 标签文本：`.label` 或等价的紧凑文本样式
- 说明/注释文本：`.caption` 或低层级文本样式

原则：

- 标题负责层级，正文负责可读性
- 除既有工具类外，不默认新增特殊字距
- 产品页优先稳定、克制，不追求海报式排版

### 5.3 间距与圆角

默认遵循紧凑的 4px 栅格节奏。

推荐节奏：

- 常用间距：8px、12px、16px、20px、24px
- 常用面板内边距：12px、16px、20px
- 默认组件圆角：4px
- 大圆角仅在现有上下文已经使用时才跟随

原则：

- 同一页面尽量只使用少量稳定的间距档位
- 不要让卡片、弹窗、按钮各自使用不同的圆角语言

### 5.4 边框与阴影

Tier0 的分层主要依赖边框，不依赖重阴影。

默认规则：

- 常规面板和表格使用中性细边框
- 弹层、下拉、弹窗可以使用适度阴影
- 日常 dashboard 卡片避免大而软的阴影
- 强描边只用于 focus、selected、danger 或画布型场景

## 6. 组件级规范

### 6.1 按钮

优先使用 `@tier0/ui` 的 `Button`。

规则：

- 一个局部决策区域通常只有一个主操作
- 黑色主按钮用于核心确认
- 绿色高亮按钮用于更强的产品强调动作
- 图标按钮保持克制，图标尺寸与周围控件一致
- 按钮文案简短，且必须走 i18n

### 6.2 表单

表单应优先保证可扫读性和可维护性。

规则：

- 优先复用共享输入组件或已有 Ant Design 表单体系
- 字段密度保持紧凑，不做营销页式大间距表单
- 校验、占位、标签、帮助文案必须国际化
- 稍复杂表单应提取 `initialValues`、`rules`、字段配置和 options
- 不要在 JSX 中内联大段字段规则和复杂 label 节点

### 6.3 弹窗

优先使用 `CnDialog`。

规则：

- 弹窗默认作为中高密度操作容器
- 标题、内容、底部操作区层级明确
- 长内容使用稳定滚动区，不让整体布局跳动
- 除特别阻断式流程外，保留清晰的关闭路径

### 6.4 表格与列表

表格和资源列表应体现“可操作工作台”的气质。

规则：

- 表头清晰但不过分抢眼
- 行 hover、selected 态使用既有中性或高亮背景
- 长文本显式处理截断、换行或 tooltip
- 行操作保持低噪音，不要每列都做强视觉按钮

### 6.5 卡片、标签与状态

卡片用于承载资源、摘要、状态块，不用于堆砌装饰。

规则：

- 卡片默认使用浅背景或白底
- 标签优先使用现有 tag 组件和状态 token
- 高亮绿表示 Tier0 强调态，不等于所有 success 态
- 状态颜色要有明确语义，不做“看起来好看”的临时配色

## 7. 页面结构规范

多数内部产品页应遵循以下基本结构：

- Header：标题、描述、返回、主操作、次操作
- Controls：搜索、筛选、分段、视图切换、批量操作
- Content：表格、列表、画布、编辑器或详情区

要求：

- loading / empty / error 状态应保持内容区结构稳定
- 使用 `min-h-0`、明确滚动容器和稳定布局边界
- 不要因为局部状态切换导致整页高度和布局频繁跳变

## 8. 交互与动效

动效服务于状态表达，不服务于装饰。

规则：

- 常规过渡聚焦在颜色、透明度、背景、边框、阴影
- 过渡时长保持短促，避免拖沓
- loading、disabled、selected、hover、focus 必须有清晰反馈
- 不使用与业务状态无关的装饰性动画

可以少量使用渐变或动态效果的场景：

- AI 思考中
- 构建中
- 需要表达“流动过程”的明确产品状态

## 9. 国际化要求

所有用户可见文案必须国际化，包括但不限于：

- 按钮
- 标题与描述
- 表单标签、占位、校验信息
- 表格列名
- 空状态、错误提示、tooltip、toast

日志和临时调试信息除外，但提交前应清理无关调试输出。

## 10. Do / Don't

Do：

- 先复用 `packages/theme` 和 `packages/ui`
- 优先使用语义 token，而不是临时颜色
- 保持高密度、清晰层级、稳定结构
- 让选中、激活、禁用、危险态都有明确反馈

Don't：

- 不要在 feature 目录里再造一套设计系统
- 不要把内部产品页做成营销风 landing page
- 不要滥用 FX Green
- 不要依赖重阴影、大渐变、强装饰做层级
- 不要写死用户可见文案
- 不要把复杂表单配置全部内联在 JSX

## 11. 风格化约束

当需求没有明确视觉稿，或只给出低保真草图时，默认按以下风格化约束执行。

### 11.1 页面气质

- 默认是产品工作台，不是品牌展示页
- 信息组织优先于装饰表达
- 视觉重点来自结构、层级和状态，而不是大色块和视觉特效
- 新页面应优先“像现有 Tier0 页面”，而不是追求单页出彩

### 11.2 布局风格

- 内部页面默认使用 workspace 结构：`Header + Controls + Content`
- 主内容区优先左对齐、上对齐，不做大面积居中排布
- 控件与信息块采用紧凑排布，避免大片留白造成“空”和“散”
- 同一区域尽量保持一致的对齐线、卡片宽度和间距节奏

禁止：

- 在内部产品页使用 landing page 式 hero 区、超大标题和大块口号文案
- 在普通业务页加入与任务无关的装饰背景、浮层图形或视觉噪音

### 11.3 色彩风格

- 默认基底始终是白、浅灰、中性边框和近黑文字
- 近黑用于主按钮、关键操作、核心信息
- FX Green 只用于高亮、激活、选中、进度、关键强调
- success / warning / error / info 必须走对应语义色，不混用高亮绿替代

禁止：

- 把 FX Green 扩大为页面主背景色
- 为单个功能模块定义新的品牌主色
- 默认使用紫蓝渐变、霓虹色、米棕色、深黑科技舱风作为新页面基调

### 11.4 组件形态

- 默认圆角 4px，除非周边上下文已经明确采用更大圆角
- 默认使用细边框和轻量背景层次，不依赖重阴影
- 按钮、输入框、表格、标签优先使用现有共享组件形态
- 列表、表格、筛选器、弹窗维持高密度和高可操作性

禁止：

- 普通卡片使用大而软的阴影作为主要分层方式
- 默认把标签、筛选项、按钮全部做成 pill 形态
- 在 feature 内随意重新定义按钮、弹窗、表格的基础视觉语言

### 11.5 排版风格

- 标题负责分层，正文负责阅读，不做海报式夸张排版
- 页面内标题层级不宜过多，通常控制在 2 到 3 层
- 描述文案保持短句、信息化、产品化，避免过度营销表达
- 数字、状态、标签、辅助信息应使用更克制的字重和颜色层级

禁止：

- 为了“有设计感”引入新的展示字体
- 在普通业务页使用过大的字阶和过强字重造成压迫感
- 用大段说明文替代结构化信息展示

### 11.6 动效风格

- 动效只用于表达 hover、focus、selected、loading、disabled、expand/collapse 等状态变化
- 常规过渡短、轻、可预期，不制造额外注意力负担
- 页面切换和区域展开优先稳定，不做强戏剧化过场

禁止：

- 与业务无关的装饰性动画
- 长时间、重复、显眼的漂浮、闪烁、呼吸类效果
- 因动效导致布局位移、内容跳动或操作目标不稳定

### 11.7 文案风格

- 文案应直接、克制、可操作，优先说明动作、状态、结果
- 按钮文案优先使用明确动词，不使用模糊口号式表达
- 空状态和错误文案应先说明当前状态，再给出下一步动作
- 同一模块内术语保持稳定，不混用多个近义词

禁止：

- 在产品界面中使用明显营销语气、情绪化语气或品牌宣传口号
- 同一动作在不同区域使用不同命名

## 12. 开发前快速检查

开始 UI 开发前，至少确认以下事项：

- 是否已有可复用的共享组件
- 是否已有对应语义 token
- 页面是否符合 workspace 型产品结构
- 用户可见文案是否已规划 i18n key
- 当前方案是否与现有页面密度和风格一致

## 13. UI Review Checklist

提交 UI 改动前，至少按以下清单自查一次。

### 13.1 风格一致性

- 页面整体是否仍然像 Tier0 的 workspace，而不是展示型 landing page
- 是否延续了现有页面的密度、边框语言、按钮语气和信息层级
- 是否出现了新的主视觉颜色、新的圆角语言或新的阴影风格
- 是否存在“单个模块特别花，但整体不协调”的情况

### 13.2 颜色与 Token

- 是否优先使用了 `--tier0-*` 语义 token 或对应 Tailwind 语义 class
- 是否出现了硬编码 hex 颜色、Tailwind 默认调色板或临时颜色变量
- highlight、success、warning、error 是否各自承担了正确语义
- selected、hover、focus、disabled、danger 是否有明确且一致的视觉反馈
- 是否已对改动文件执行 `pnpm check:ui-tokens -- <file-or-dir>`

### 13.3 组件复用

- 是否优先复用了 `@tier0/ui` 和现有业务组件
- 是否在 feature 目录里重新做了按钮、弹窗、表格、标签、输入框基础样式
- 新增局部样式是否真的无法通过共享组件或 token 解决

### 13.4 布局与信息结构

- 页面是否仍然遵循 `Header + Controls + Content` 的基本组织方式
- 内容区是否有稳定的 loading / empty / error 状态容器
- 是否存在滚动区域不清晰、布局跳动、内容挤压或留白失衡问题
- 长文本、长列表、窄屏场景是否处理了截断、换行和溢出

### 13.5 文案与交互

- 所有用户可见文案是否都已国际化
- 按钮文案、空状态、错误提示是否直接、清晰、可操作
- 动效是否只服务于状态表达，而不是装饰
- 关键操作是否足够明显，次要操作是否保持克制

### 13.6 复杂场景专项检查

- 表单：是否提取 `initialValues`、`rules`、字段配置和 options
- 表格：是否处理了列宽、tooltip、批量操作、状态标签和行操作噪音
- 弹窗：是否有稳定高度、清晰标题层级、合理关闭路径和可滚动区
- 卡片：是否通过结构和状态建立层次，而不是靠重装饰和强阴影

## 14. 相关参考

- `CLAUDE.md`：工程规范、架构边界、流程门禁、仓库级硬约束
- `.claude/skills/references/tailwind-tokens.md`：Tailwind token 三层映射、语义 class 速查、违规 class 扫描规则
- `packages/theme`：主题与 token 的代码事实来源
- `packages/ui`：共享组件的代码事实来源

`DESIGN.md` 负责回答“界面应该长什么样、为什么这样设计”。
`tailwind-tokens.md` 负责回答“在 JSX 里具体该写哪个 class、如何做样式门禁”。

因此更合适的做法是：

- 在 `DESIGN.md` 中保留颜色与 token 的原则性约束
- 在 `tailwind-tokens.md` 中保留实现层速查表和扫描命令
- 两者互相引用，不整篇合并，避免文档职责再次混杂

## 15. 与其他文档的分工

- `CLAUDE.md`：工程规范、架构边界、流程门禁、仓库级硬约束
- `DESIGN.md`：UI 设计方向、视觉规则、组件风格与页面结构原则
- `packages/theme`：主题与 token 的代码事实来源
- `packages/ui`：共享组件的代码事实来源

如果某条规则会影响仓库工程边界、开发流程或提交门禁，应写在 `CLAUDE.md`。
如果某条规则主要用于保证界面风格一致性，应写在 `DESIGN.md`。
